# 02. Husky + lint-staged + commitlint

> Этап 0.3 плана. Результат: плохой код и плохое сообщение коммита не проходят **ещё до коммита**, прямо у тебя на компьютере.
> Всё настраиваешь **ты**, я проверяю.

Версии на момент написания: `husky` 9.1.7, `lint-staged` 17.5.1, `@commitlint/cli` 21.2.2.

---

## 1. Зачем это, если уже есть CI

CI проверяет код **после** push: ты запушил → через минуту узнал, что упало → чинишь → пушишь снова. Это медленно, а упавшие коммиты остаются в истории ветки.

Husky проверяет **до** коммита, за пару секунд. Две линии защиты:

```
ты пишешь код
     │
     ▼
git commit ──▶ [Husky: pre-commit]  lint + prettier на изменённых файлах  ← 1-я линия, локально, секунды
     │         [Husky: commit-msg]  проверка сообщения коммита
     ▼
git push ────▶ [GitHub Actions CI]  lint, prettier, тесты, build          ← 2-я линия, на сервере, минуты
     │
     ▼
merge в main
```

Зачем нужны обе: локальные хуки **можно обойти** (`git commit --no-verify`), а у коллеги они могут быть не установлены. CI обойти нельзя. Husky даёт быструю обратную связь, CI — гарантию.

## 2. Три инструмента — три роли

| Инструмент      | Роль                                                                                                           |
| --------------- | -------------------------------------------------------------------------------------------------------------- |
| **Husky**       | Запускает твои команды на событиях git (перед коммитом, при вводе сообщения, перед push)                       |
| **lint-staged** | Прогоняет линтер и форматтер **только по файлам, которые ты добавил в коммит** (staged), а не по всему проекту |
| **commitlint**  | Проверяет, что сообщение коммита соответствует формату Conventional Commits                                    |

Husky сам ничего не проверяет — это «будильник», который вызывает lint-staged и commitlint в нужный момент.

## 3. Git hooks — на чём всё построено

**Git hook** — скрипт, который git сам запускает на определённом событии. Git умеет это давно, без всяких библиотек. Основные хуки:

| Хук          | Когда срабатывает                           | Что обычно делают                    |
| ------------ | ------------------------------------------- | ------------------------------------ |
| `pre-commit` | после `git commit`, **до** создания коммита | линт и форматирование                |
| `commit-msg` | когда сообщение уже написано                | проверка формата сообщения           |
| `pre-push`   | после `git push`, **до** отправки           | тесты (дольше, поэтому не на коммит) |

Если скрипт хука вернул код выхода ≠ 0, **git отменяет действие**. Та же логика, что в CI: exit code решает всё.

**Проблема без Husky.** Хуки лежат в `.git/hooks/`, а папка `.git/` **не попадает в репозиторий**. Ты настроил хук, но коллега склонировал проект — и у него хуков нет.

**Как это решает Husky:**

1. Хуки лежат в папке **`.husky/`** — она в репозитории, её видят все.
2. В `package.json` появляется скрипт `"prepare": "husky"`. `prepare` npm запускает **автоматически после `npm install`**.
3. Эта команда говорит git: «бери хуки из `.husky/`» (выставляет `core.hooksPath`).

Итог: любой, кто склонировал проект и сделал `npm install`, автоматически получает все хуки. Именно в этом смысл Husky.

## 4. Conventional Commits — формат сообщений

```
<тип>(<область>): <описание>

feat(users): add user deletion
fix(header): correct timer format
ci: add GitHub Actions workflow
```

| Тип        | Когда                                                         |
| ---------- | ------------------------------------------------------------- |
| `feat`     | новая функциональность                                        |
| `fix`      | исправление бага                                              |
| `refactor` | переделка кода без изменения поведения                        |
| `style`    | форматирование, пробелы, точки с запятой — логика не меняется |
| `test`     | тесты                                                         |
| `docs`     | документация                                                  |
| `ci`       | CI-конфиги                                                    |
| `build`    | сборка, зависимости                                           |
| `chore`    | прочая рутина (конфиги, инструменты)                          |
| `perf`     | оптимизация производительности                                |
| `revert`   | откат коммита                                                 |

Правила пресета `config-conventional`, на которых чаще всего спотыкаются:

- тип — **маленькими буквами** из списка выше (`Feat:` или `feature:` не пройдут);
- после двоеточия — **пробел**;
- описание не пустое и **без точки в конце**;
- заголовок не длиннее 100 символов.

Зачем это нужно: история читается как список изменений; по коммитам можно автоматически сгенерировать CHANGELOG и посчитать новую версию (`fix` → 1.0.**1**, `feat` → 1.**1**.0, `feat!` или `BREAKING CHANGE` → **2**.0.0). На собеседовании про Conventional Commits спрашивают часто.

## 5. Установка — пошагово

Все команды — в PowerShell, по одной.

**0.** Ветка:

```bash
git checkout -b chore/husky
```

**1.** Установить пакеты. `-D` значит devDependencies: они нужны при разработке, а в собранное приложение не попадают:

```bash
npm install -D husky lint-staged @commitlint/cli @commitlint/config-conventional
```

**2.** Инициализировать Husky:

```bash
npx husky init
```

Команда делает две вещи — проверь обе:

- в `package.json` → `scripts` появился `"prepare": "husky"`;
- создан файл `.husky/pre-commit`, внутри строка `npm test`.

**3.** Открой в VS Code `.husky/pre-commit` и **замени** его содержимое на:

```sh
npx lint-staged
```

Почему не `npm test`: тесты гоняются по всему проекту, это долго, а на каждый коммит нужна мгновенная проверка. Тесты уже есть в CI; позже, если захочешь, их можно повесить на `pre-push`.

**4.** Настрой lint-staged — добавь в `package.json` новый ключ верхнего уровня (рядом со `scripts`, не внутрь):

```json
"lint-staged": {
  "*.{ts,html}": "eslint --fix",
  "*.{scss,css,json,md,yml,yaml}": "prettier --write"
}
```

Как это читать: «для staged-файлов `.ts` и `.html` запусти `eslint --fix`, для остальных — `prettier --write`». Пути к файлам lint-staged подставит сам — **не дописывай их** в команду.

Почему для `.ts` и `.html` нет `prettier`: в `eslint.config.js` подключён `eslintPluginPrettierRecommended`, то есть Prettier уже работает **внутри** ESLint как одно из правил. `eslint --fix` и отформатирует, и починит то, что можно починить автоматически. Запуск Prettier второй раз был бы дублированием.

`--fix` / `--write` исправляют файлы, и lint-staged **сам добавит исправления в коммит**. Если же ESLint нашёл ошибку, которую автоматически не исправить, — коммит отменяется.

**5.** Конфиг commitlint — создай в корне проекта файл **`commitlint.config.js`**:

```js
module.exports = {
  extends: ['@commitlint/config-conventional'],
};
```

`module.exports` (CommonJS), а не `export default`: в нашем `package.json` нет `"type": "module"`, проект в режиме CommonJS — так же, как `eslint.config.js`.

**6.** Хук для сообщений: в VS Code создай файл **`.husky/commit-msg`** (правой кнопкой по папке `.husky` → New File), внутри одна строка:

```sh
npx --no -- commitlint --edit $1
```

Разбор: `$1` — путь к временному файлу, куда git положил текст сообщения; `--edit $1` — «проверь сообщение из этого файла». `--no` запрещает `npx` что-то скачивать, если пакет вдруг не установлен.

> ⚠️ **Создавай файл именно в VS Code, а не через `echo "..." > .husky/commit-msg` в PowerShell 5.1.** PowerShell 5.1 пишет в начало файла невидимую метку кодировки (BOM), и хук сломается с непонятной ошибкой вида `command not found`. В документации Husky пример именно через `echo` — он рассчитан на Linux/macOS.

**7.** Защита от проблемы с переносами строк. У тебя в git включён `core.autocrlf=true`: на Windows git превращает концы строк LF в CRLF. Хуки — это shell-скрипты, и символ `\r` из CRLF может их ломать (особенно у того, кто склонирует проект заново). Создай в корне файл **`.gitattributes`**:

```
.husky/* text eol=lf
```

Это указание git: файлы в `.husky/` всегда хранить и выдавать с LF. Пусть это будет твоей привычкой для любых shell-скриптов в репозитории.

## 6. Проверка: сломай специально

Настройку считаем рабочей, только когда хуки **поймали** ошибку. Проверь три сценария:

**Сценарий 1 — плохое сообщение коммита:**

```bash
git add .
```

```bash
git commit -m "добавил хаски"
```

Ожидаемо: commitlint отклонит коммит (`subject may not be empty`, `type may not be empty`). Потом правильно:

```bash
git commit -m "chore: set up husky, lint-staged and commitlint"
```

**Сценарий 2 — ошибка линтера блокирует коммит.** Временно добавь в любой `.ts`-файл:

```ts
interface User {
  name: string;
}
```

Правило `naming-convention` у нас требует префикс `I` у интерфейсов с уровнем `error`. Сделай `git add` этого файла и попробуй закоммитить → коммит должен **отмениться**. Потом удали эти строки.

(`console.log` для проверки не подойдёт: у этого правила уровень `warn`, а предупреждения коммит не блокируют. Это важная разница между `warn` и `error`.)

**Сценарий 3 — автоформатирование.** В любом `.scss` сломай отступы (например, добавь лишние пробелы), закоммить → Prettier сам исправит файл, и в коммит попадёт уже отформатированная версия.

**Ручная проверка commitlint** без коммита:

```bash
echo "feat: add login page" | npx commitlint
```

## 7. Как обойти хуки и почему это плохая идея

```bash
git commit -m "..." --no-verify
```

`--no-verify` пропускает `pre-commit` и `commit-msg`. Бывает оправдано — например, для экстренного hotfix, когда хук сломан. Но **любой** может так сделать, поэтому хуки — это удобство, а не защита. Защита — CI (и в будущем защищённая ветка `main`).

Отсюда задание со звёздочкой: добавь в `ci.yml` проверку сообщений коммитов в PR — тогда `--no-verify` не поможет. Подсказка: у commitlint есть руководство по CI (commitlint.js.org → Guides → CI setup), нужны `fetch-depth: 0` в checkout и `npx commitlint --from ... --to ...`.

## 8. Частые проблемы

| Симптом                                             | Причина / решение                                                                                                                       |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Хуки вообще не срабатывают                          | Не выполнился `prepare`. Запусти `npm install` (или `npx husky`) и проверь `git config core.hooksPath` — должно быть `.husky/_`         |
| `command not found` в первой строке хука            | BOM или CRLF в файле хука. Пересоздай файл в VS Code; в правом нижнем углу VS Code должно быть **LF** и **UTF-8** (не «UTF-8 with BOM») |
| lint-staged ругается `no staged files`              | Ты не сделал `git add` — lint-staged смотрит только на staged-файлы                                                                     |
| Коммит проходит, хотя есть `console.log`            | Это `warn`, а не `error` — так и задумано в `eslint.config.js`                                                                          |
| В CI на `npm ci` что-то про husky                   | В CI `prepare` тоже запускается — это нормально. Отключить можно переменной окружения `HUSKY=0`                                         |
| `commitlint.config.js`: `Unexpected token 'export'` | Написал `export default` в CommonJS-проекте → используй `module.exports`                                                                |

## 1. Зачем Husky, если есть CI, и наоборот

Они решают разные задачи и работают в разное время.

**Husky — скорость и удобство.** Проверка проходит локально за секунды, ещё до того, как коммит создан. Ты не тратишь минуты на цикл «запушил → подождал → узнал → починил → снова запушил», и в истории ветки не остаётся мусорных коммитов вида «fix lint».

**CI — гарантия.** Хуки можно обойти (`--no-verify`), можно не установить (не сделал `npm install`), можно удалить. У коллеги может не быть твоих настроек. CI выполняется на сервере GitHub, его обойти нельзя, и он один для всех.

Формула: **Husky — предохранитель для себя, CI — контракт для команды.** Поэтому нужны оба.

## 2. Почему хуки из `.git/hooks` не передаются

Потому что `.git/` — служебная папка, и она **не является частью содержимого репозитория**. Git версионирует файлы проекта, а не собственную служебную директорию. При `git clone` создаётся новая `.git/` со стандартными примерами хуков (`*.sample`), и твои хуки туда не попадают.

**Как решает Husky** — в три шага:

1. Хуки лежат в `.husky/` — это обычная папка проекта, она коммитится и уезжает на GitHub.
2. В `package.json` есть `"prepare": "husky"`.
3. При `npm install` этот скрипт выполняет `git config core.hooksPath .husky/_` — то есть говорит git искать хуки не в `.git/hooks`, а в папке проекта.

Проверить можно командой:

```bash
git config core.hooksPath
```

У тебя сейчас выводит `.husky/_` — значит, всё подключено.

## 3. Что делает `prepare`

`prepare` — один из **lifecycle-скриптов** npm: их npm запускает сам в определённые моменты, без твоего участия (`pre*`, `post*`, `prepare`, `prepublish` и т.д.).

`prepare` выполняется:

- **после `npm install`** и после `npm ci` — это наш случай;
- перед публикацией пакета в npm.

Husky использует его как точку автоматической установки: любой, кто склонировал проект и поставил зависимости, автоматически получает рабочие хуки. Именно поэтому его вписывают в `prepare`, а не в `postinstall`.

## 4. Зачем lint-staged

Три причины:

1. **Скорость.** В нашем проекте линт всего кода занимает секунды, но в реальном проекте на тысячи файлов — минуты. Такое на каждый коммит никто терпеть не будет.
2. **Ответственность за своё.** Линтер по всему проекту вывалит ошибки в чужих и легаси-файлах, которых ты не касался. Ты либо чинишь чужое, либо привыкаешь игнорировать красное — оба варианта плохи.
3. **Проверяется именно то, что уйдёт в коммит.** lint-staged берёт **staged-версию** файлов. Если в рабочей копии у тебя есть изменения, которые ты не добавил через `git add`, они в коммит не попадут — и проверять их незачем.

Бонус: автоисправления (`eslint --fix`, `prettier --write`) lint-staged сам добавляет в коммит.

## 5. Хуки git

| Хук                            | Когда                                    | Что обычно вешают                                        |
| ------------------------------ | ---------------------------------------- | -------------------------------------------------------- |
| `pre-commit`                   | до создания коммита                      | lint-staged: линт и формат                               |
| `prepare-commit-msg`           | до открытия редактора сообщения          | автоподстановка шаблона или номера задачи из имени ветки |
| `commit-msg`                   | сообщение написано, коммит ещё не создан | commitlint                                               |
| `pre-push`                     | до отправки на сервер                    | тесты, сборка — то, что дольше пары секунд               |
| `post-merge` / `post-checkout` | после merge или смены ветки              | `npm install`, если изменился `package-lock.json`        |

У нас заняты первый и третий. Тесты не вешаем на коммит специально: они идут почти 10 секунд, для коммита это много. Логичное место для них — `pre-push` или CI.

## 6. `feat(auth)!: drop legacy login`

| Часть               | Значение                                           |
| ------------------- | -------------------------------------------------- |
| `feat`              | тип: новая функциональность                        |
| `(auth)`            | scope — область изменений, здесь фича авторизации  |
| `!`                 | **breaking change**: ломает обратную совместимость |
| `drop legacy login` | описание                                           |

Перевод: «в модуле авторизации убран старый механизм входа, это ломающее изменение».

**По semver** (`MAJOR.MINOR.PATCH`):

- `fix` → PATCH: `1.4.2` → `1.4.3`
- `feat` → MINOR: `1.4.2` → `1.5.0`
- **`!` или `BREAKING CHANGE:` в теле → MAJOR: `1.4.2` → `2.0.0`**

Здесь есть `!`, поэтому версия станет `2.0.0` — несмотря на то, что тип `feat`. Восклицательный знак сильнее типа. Именно так работают автоматические релизы: инструмент читает коммиты и сам считает новую версию.

## 7. Почему `console.log` не блокирует, а интерфейс без `I` — блокирует

Всё решает **уровень правила** в `eslint.config.js` и код выхода:

```js
'no-console': ['warn', { allow: ['warn', 'error'] }],   // предупреждение
'@typescript-eslint/naming-convention': ['error', ...]   // ошибка
```

- **`warn`** — ESLint печатает предупреждение, но завершается с кодом **0**. Для git это «успех», коммит создаётся.
- **`error`** — ESLint завершается с кодом **1**. Хук вернул не ноль → git отменяет операцию.

Это ровно тот же механизм exit code, что и в CI. Идея разделения: `error` — то, что недопустимо в коде; `warn` — то, что нежелательно, но иногда оправданно (временный лог при отладке).

Если захочешь, чтобы и предупреждения блокировали, к eslint добавляют флаг `--max-warnings=0`.

## 8. Как обойти хуки и почему на них нельзя полагаться

Способов много:

```bash
git commit -m "..." --no-verify
```

- переменная окружения `HUSKY=0` отключает Husky целиком;
- можно не выполнять `npm install` — и хуков просто не будет;
- можно вручную сбросить `core.hooksPath` или удалить папку `.husky`.

Всё это доступно **любому** разработчику, и никто об этом не узнает. Поэтому хуки — **удобство, а не гарантия**. Гарантию даёт только то, что выполняется на сервере и не зависит от настроек чужого компьютера: **CI + защита ветки**. У нас обе части уже есть: даже если ты обойдёшь хук локально, CI поймает ошибку, а правило `protect-main` не даст смёржить красный PR.
